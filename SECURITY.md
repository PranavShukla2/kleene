# Security Policy

## Reporting a vulnerability

Please report security issues privately, not as a public issue.

Use GitHub's [private vulnerability
reporting](https://github.com/PranavShukla2/kleene/security/advisories/new), or email
**pranavmshukla@gmail.com**.

Include what you did, what happened, and — if you have one — a share link or `.kln` file that
reproduces it. I will acknowledge within a week and tell you either what the fix is or why I
think it isn't an issue. If you'd like credit in the advisory, say so.

This is a personal project maintained by one person, so I can't promise an SLA. I can promise
you'll get a real answer.

## Supported versions

The deployed site at [kleene.pranavmshukla.in](https://kleene.pranavmshukla.in) always runs
the latest release, and that is the version fixes land in. Older tags are not patched.

## What the threat model actually is

Kleene has no backend, no accounts and no database. Nothing is uploaded and nothing is stored
on a server. That removes most of the categories a security policy usually covers, and it is
worth being precise about what it leaves.

**Everything runs in your browser.** The engine is WebAssembly compiled from Rust; your
machines live in your tab's local storage and in files you save yourself. There is no server
holding your work, so there is nothing on one to breach.

**A share link carries the machine in the URL fragment.** The part after `#` is never sent to
any server by any browser — it does not appear in request logs, including the static host's.
But a link is still readable by anyone who has it, and it will sit in the history of every
browser it's opened in. Treat a share link as public.

**Imported files are parsed by code that runs on your machine.** `.kln` and JFLAP `.jff`
files are handled entirely client-side. The Rust core is `#![forbid(unsafe_code)]` and
WebAssembly is memory-sandboxed, so a malformed file should produce an error rather than
anything worse. A file that instead causes a crash, a hang, or an escape from the sandbox
**is a vulnerability** — please report it.

**Long-running conversions are a known, bounded limit, not a vulnerability.** State
elimination is worst-case exponential; 33 states already produces a 177,000-character
expression. There are explicit caps (`STEP_CAP`, `ELIMINATION_LIMIT`) and they refuse rather
than hang. A machine that gets _past_ those caps and freezes the tab is worth reporting; one
that hits them and says so is working as intended.

### In scope

- Cross-site scripting, including through an imported file, a share link, or a state name.
- Anything that escapes the WebAssembly sandbox or corrupts memory.
- A crafted `.kln` or `.jff` that hangs or crashes the tab.
- Service-worker or cache poisoning that could serve altered code.
- A dependency with a known advisory that we actually reach.

### Not in scope

- Missing headers with no demonstrated impact on a static, backendless site.
- Denial of service against your own browser tab by feeding it a huge machine — that is the
  bounded-cost case above.
- Anything requiring an attacker to already control the user's machine or browser extensions.
- Reports generated by a scanner with no working proof of concept.
